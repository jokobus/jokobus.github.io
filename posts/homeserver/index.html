0. Introduction & Motivation

tl;dr: Raspberry Pi 4 (8GB) with 64-bit OS booting directly from a 4TB GPT NVMe SSD (no SD card!), running Docker Compose, Caddy Reverse Proxy with automatic HTTPS, Nextcloud AIO, Vaultwarden, Immich, Homebox, and Fail2ban intrusion defense.

This guide documents the complete, battle-tested setup and long-term operation of a private, energy-efficient homeserver. The system serves as your private cloud for file synchronization, password management, high-resolution photo libraries, and home inventory—all while giving you 100% control and ownership of your personal data.

All the software components used in this guide are widely adopted in the open-source community. However, piecing together SSD firmware booting, GPT partitioning on ARM, Docker networking, automatic Let’s Encrypt TLS reverse proxying, and multi-jail intrusion defense can be daunting if you have to search through dozens of disconnected forum posts. This guide brings everything together into a coherent, structured, and beginner-friendly blueprint.

Be confident: Even if you are relatively new to Linux, terminal commands, or self-hosting, every single step—from assembling the hardware to recovering individual files from encrypted backups—is explained clearly with rationale and context.

Take your time: When all parts are on your desk, following this guide, flashing the system, formatting the drive, and launching the services typically takes half a day.

0.1 Goals & Scope of the Project

When designing this setup, the following architectural goals guided every hardware, software, and configuration decision:

  • Low Power Consumption: Consumes only 4–7 Watts under typical idle and light workloads—less than a standard Wi-Fi router.
  • Silent Operation: Completely passive cooling without fans, making it ideal for living rooms, bedrooms, or home offices.
  • High Reliability & Durability: Booting directly from a fast NVMe SSD over USB 3.0 eliminates the wear, corruption, and speed bottlenecks of microSD cards.
  • Complete Data Sovereignty: Pure open-source software with no vendor lock-in, telemetry, or recurring cloud subscription fees.
  • Seamless Global Access: Encrypted HTTPS subdomains accessible from web browsers, desktop sync clients, and mobile apps worldwide.
  • Enterprise-Grade Security: Automated TLS certificates via Caddy, hardened HTTP security headers, local-only administrative panel restrictions, and real-time Fail2ban IP banning.
  • Effortless Extensibility: Because the entire system runs on Docker Compose, you can easily add other containers later, such as Pi-hole, Home Assistant, or Jellyfin. (To host a static blog or website behind Caddy, see our Hugo & GitHub Actions Deployment Guide).

What This Server Is Not Intended For:

  • Massive Enterprise Transcoding: While Immich handles photo and video backups smoothly, heavy multi-user 4K video transcoding clusters require dedicated x86 CPUs or discrete GPUs.
  • High-Concurrency Video Conferencing: While Nextcloud includes a “Talk” video chat app, running multi-party video conferences on a Raspberry Pi can quickly saturate the CPU. For video meetings, dedicated hardware or external communication services remain more practical.

1. Hardware Selection & Preparation

Building a quiet, stable homeserver requires carefully matched components. Below are the exact parts used for this build, along with the reasoning behind each choice so you can adapt them to what you already own.

1.1 Raspberry Pi 4 Model B (8GB)

  • Model: Raspberry Pi 4 Model B with 8GB RAM.
  • Why 8GB?: Running PostgreSQL, Redis, Nextcloud PHP workers, and Immich machine learning simultaneously needs memory. The 8GB model provides ample breathing room—under typical idle conditions, RAM usage hovers around 15–25% and CPU stays well below 10%.
  • Why Pi 4 instead of Pi 3 or Pi 5?:
    • Compared to Pi 3: The Pi 4 offers true Gigabit Ethernet (not throttled over USB), separate USB 3.0 buses, and double/quadruple the RAM.
    • Compared to Pi 5: When this project began, the Pi 4 was the benchmark. The Pi 4 consumes less idle power and runs cooler under passive heatsinks than the Pi 5, making it the sweet spot for an always-on, silent home appliance.
    • Can you use a Pi 5? Yes! If you already have a Pi 5 or want extra compute power for heavy indexing, it will work great. Just note that the Pi 5 usually benefits from active cooling (a quiet fan) to avoid thermal throttling under sustained load. If you have an older Pi lying around, you can also use it to test, though memory will be more constrained.

1.2 Official Raspberry Pi 15.3W USB-C Power Supply

  • Specs: 5.1V / 3.0A DC via USB-C.
  • Why Quality Matters: The external NVMe SSD draws power directly from the Raspberry Pi’s USB 3.0 port. Low-grade phone chargers often drop voltage under load (“undervoltage warnings”), which can cause sudden restarts or filesystem corruption. The official power supply provides a rock-solid 5.1V rail.

1.3 Passive Aluminum Heatsink Case

  • Type: Solid aluminum enclosure (e.g., Geekworm N300, Flirc, or Argon NEO).
  • Thermal Performance: Thermally conductive pads bridge the Broadcom SoC and RAM directly to the aluminum chassis. This turns the entire case into a massive heatsink, keeping CPU temperatures between 38°C and 48°C under normal room conditions without a single moving part.
  • Placement: Place the unit on an open shelf, desk, or sideboard where natural air circulation is present. Avoid stuffy, closed, unventilated cabinets.

1.4 Temporary MicroSD Card (16GB–64GB)

  • Used only once during the initial setup to flash the bootloader and transfer the operating system onto the GPT-partitioned SSD. Once the SSD is set up to boot natively, the microSD card is ejected and can be repurposed.

1.5 M.2 NVMe SSD (e.g., Crucial P3 4TB)

  • Form Factor: M.2 2280 PCIe Gen3 NVMe.
  • Capacity: 4TB ensures plenty of space for full-resolution photo libraries, personal file archives, Nextcloud document history, and database backups for years to come.
  • Partitioning Note: Any drive larger than $2\,\text{TB}$ requires a GPT (GUID Partition Table) rather than legacy MBR, which we configure in Chapter 2.

1.6 USB 3.1 Gen 2 to NVMe M.2 Enclosure

  • Enclosure: Aluminum USB-C to M.2 NVMe enclosure (e.g., ORICO, Sabrent, or ICY BOX with JMS583, RTL9210, or ASM2362 bridge chipsets).
  • Port: Always connect the enclosure to one of the blue USB 3.0 ports on the Raspberry Pi for maximum throughput.

1.7 External Backup Drive (Old HDD or SSD)

  • A 2.5’’ or 3.5’’ external USB hard drive (e.g. 4TB+) formatted as btrfs or ext4. An older external USB drive you already have at home is great for this. It connects to the second USB 3.0 port and receives automated daily Borg backups.

1.8 Ethernet Cable

  • Connect the Raspberry Pi directly to a Gigabit LAN port on your home router or switch. Always prefer wired Ethernet over Wi-Fi for server reliability, consistent ping times, and full file-transfer bandwidth.

2. Raspberry Pi OS Installation on a GPT SSD

Standard Raspberry Pi OS disk images come formatted with an MBR partition table, which hard-limits partition capacity to $2\,\text{TB}$. To unlock the full 4TB NVMe SSD, we initialize the SSD with a GPT partition table, transfer the operating system from a temporary SD card, and configure the Pi’s bootloader to boot straight from USB.

Step 2 Overview:
1. Flash Pi OS to temporary SD card with user 'hsa' & SSH enabled
2. Boot Pi from SD card with 4TB SSD plugged into USB 3.0
3. Format SSD with GPT: bootfs (512MB), rootfs (64GB), swap (16GB), data (3.8TB)
4. Clone system from SD to SSD using rsync
5. Update PARTUUIDs in cmdline.txt and /etc/fstab
6. Eject SD card and boot natively from SSD

2.1 Flashing Pre-Configured Pi OS to MicroSD Card

  1. Connect the temporary microSD card to your workstation (PC or laptop).
  2. Download and open the official Raspberry Pi Imager (v1.9 or newer).
  3. Choose Device: Raspberry Pi 4.
  4. Choose OS: Raspberry Pi OS (64-bit) (Debian Bookworm with desktop or Lite).

  1. Click Next and select Edit Settings (OS Customisation):

  • General Tab:
    • Set Hostname: kronos
    • Set Username: hsa (Home Server Admin)
    • Set Password: NobodyKnows42 (choose your own strong passphrase)
    • Wireless LAN: Leave blank (we use wired Ethernet).
    • Locale & Timezone: Set to your location (e.g. Europe/Berlin).
  • Services Tab:
    • Check Enable SSH.
    • Choose Allow public-key authentication only (or password authentication if you haven’t generated SSH keys yet).

  • SSH Key Pair: Click Run SSH-Keygen inside the imager to automatically generate an Ed25519 key pair, or paste your existing public key from ~/.ssh/id_ed25519.pub.

    If you prefer generating the key manually on your workstation terminal:

    ssh-keygen -t ed25519 -C "hsa@kronos"

    Paste the resulting line (ssh-ed25519 AAAAC3... hsa@kronos) into the authorized keys field.

  1. Save the settings, write the image to the microSD card, and let the verification step complete.

2.2 Booting from SD & Partitioning the GPT SSD

  1. Insert the microSD card into the Raspberry Pi.

  2. Connect the Ethernet cable, plug the 4TB NVMe SSD enclosure into a blue USB 3.0 port, and plug in the power supply.

  3. Wait about 60 seconds for the initial boot. Open a terminal on your computer and connect via SSH:

    ssh hsa@kronos

    (If your local network cannot resolve kronos yet, check your router’s web interface for the Pi’s IP address and run ssh hsa@192.168.178.50).

  4. Verify that the SSD is recognized by the Linux kernel:

    lsblk -o NAME,SIZE,FSTYPE,TYPE,MOUNTPOINT

    Typically, /dev/mmcblk0 is the temporary SD card and /dev/sda is your external 4TB SSD.

[!WARNING] Check device names carefully! In the next step, /dev/sda will be completely partitioned and formatted. Ensure /dev/sda corresponds to your 4TB SSD size before proceeding.

  1. Create a fresh GPT partition table on /dev/sda:

    sudo parted /dev/sda --script mklabel gpt

  2. Partition the SSD into four dedicated areas:

    • Partition 1 (/dev/sda1 - bootfs): 512 MiB FAT32 partition for Raspberry Pi bootloader firmware:
      sudo parted /dev/sda --script mkpart bootfs fat32 4MiB 516MiB
sudo mkfs.vfat -F 32 -n bootfs /dev/sda1
    • Partition 2 (/dev/sda2 - rootfs): 64 GiB ext4 partition for the Linux operating system, binaries, and system logs:
      sudo parted /dev/sda --script mkpart rootfs ext4 516MiB 64.5GiB
sudo mkfs.ext4 -L rootfs /dev/sda2
    • Partition 3 (/dev/sda3 - swap): 16 GiB Linux swap partition (provides extra virtual memory margin under heavy container operations):
      sudo parted /dev/sda --script mkpart swap linux-swap 64.5GiB 80.5GiB
sudo mkswap -L swap /dev/sda3
    • Partition 4 (/dev/sda4 - data): Remaining disk space (~3.8 TB) formatted with Btrfs for personal cloud files, databases, and container persistent volumes:
      sudo parted /dev/sda --script mkpart data btrfs 80.5GiB 100%
sudo mkfs.btrfs -L data /dev/sda4

2.3 Cloning System Files from SD to SSD

Now we copy the running operating system from the SD card onto the SSD partitions using rsync, which preserves all file permissions, extended attributes, and ownerships.

  1. Unmount the SD card boot partition:

    sudo umount /boot/firmware 2>/dev/null || sudo umount /boot 2>/dev/null || true

  2. Copy the boot firmware bit-for-bit to the SSD boot partition:

    sudo dd if=/dev/mmcblk0p1 of=/dev/sda1 bs=4M status=progress

  3. Mount the SSD root filesystem and sync all operating system files:

    sudo mkdir -p /mnt/new
sudo mount /dev/sda2 /mnt/new
sudo rsync -axHAX --progress / /mnt/new/

  4. Create essential system mount points on the new root filesystem:

    sudo mkdir -p /mnt/new/{boot/firmware,mnt/sda4,dev,proc,sys}
sudo mount /dev/sda1 /mnt/new/boot/firmware

  5. Read the unique PARTUUID strings of your new SSD partitions:

    sudo blkid -o export /dev/sda1 /dev/sda2 /dev/sda3 /dev/sda4

    Note down the PARTUUID=... values for each partition. For example:

    • /dev/sda1: PARTUUID=a1b2c3d4-01
    • /dev/sda2: PARTUUID=a1b2c3d4-02
    • /dev/sda3: PARTUUID=a1b2c3d4-03
    • /dev/sda4: PARTUUID=a1b2c3d4-04

  6. Update Kernel Boot Parameters (cmdline.txt): Tell the Linux kernel which partition contains the root operating system on boot:

    sudo nano /mnt/new/boot/firmware/cmdline.txt

    Locate root=... and replace it with the PARTUUID of /dev/sda2:

    console=serial0,115200 console=tty1 root=PARTUUID=<PARTUUID-OF-SDA2> rootfstype=ext4 fsck.repair=yes rootwait quiet splash

  7. Configure the Filesystem Table (/mnt/new/etc/fstab): Tell the operating system how to mount the SSD partitions during boot:

    sudo nano /mnt/new/etc/fstab

    Replace the contents with:

    proc                                            /proc           proc    defaults          0       0
PARTUUID=<PARTUUID-OF-SDA1>                     /boot/firmware  vfat    defaults          0       2
PARTUUID=<PARTUUID-OF-SDA2>                     /               ext4    defaults,noatime  0       1
PARTUUID=<PARTUUID-OF-SDA3>                     none            swap    sw                0       0
PARTUUID=<PARTUUID-OF-SDA4>                     /mnt/sda4       btrfs   defaults,noatime  0       0

    (Replace <PARTUUID-OF-...> with your actual IDs from step 5).

  8. Unmount temporary directories and shut down the Raspberry Pi:

    sudo umount /mnt/new/boot/firmware
sudo umount /mnt/new
sudo poweroff

2.4 First Native Boot from SSD

  1. Unplug the USB-C power cable from the Raspberry Pi.
  2. Eject the microSD card from the slot underneath the board.
  3. Plug the power cable back in.
  4. The Raspberry Pi bootloader will automatically search for bootable USB devices, find /dev/sda1 on your SSD, and boot directly into the OS.
  5. After about 45 seconds, reconnect via SSH from your computer:
    ssh hsa@kronos
  6. Confirm the system is running entirely on the SSD:
    lsblk
    You should see / mounted on /dev/sda2 and /mnt/sda4 mounted on /dev/sda4. Congratulations—your server is now running natively on the 4TB SSD!
Troubleshooting: What to do if the Pi does not boot from USB

If the green LED flashes continuously or the server doesn’t appear on your network without the SD card:

  1. Re-insert the SD card, boot up, and check your Raspberry Pi EEPROM firmware:
    sudo rpi-eeprom-update
  2. If an update is available, install it:
    sudo rpi-eeprom-update -a
sudo reboot
  3. Open the Raspberry Pi configuration utility:
    sudo raspi-config
    Navigate to Advanced Options $\rightarrow$ Boot Order $\rightarrow$ USB Boot (select USB first, fallback to SD card).
  4. Verify your cmdline.txt and /etc/fstab in /mnt/new to ensure no typos exist in the PARTUUID strings.

3. Base OS Configuration & Hardening

With the operating system booting cleanly from SSD, we configure performance optimizations, disable unused radios, set up a local firewall, and install handy maintenance scripts.

3.1 Disabling Wi-Fi and Bluetooth

Because the server is permanently connected via Ethernet, disabling the onboard Wi-Fi and Bluetooth chips saves energy, reduces heat, and eliminates potential wireless attack vectors.

Edit /boot/firmware/config.txt:

sudo nano /boot/firmware/config.txt

Add to the bottom of the file:

# Disable onboard Bluetooth and Wi-Fi
dtoverlay=disable-bt
dtoverlay=disable-wifi

Disable the corresponding system services:

sudo systemctl disable hciuart.service bluealsa.service bluetooth.service

3.2 Host Firewall & Port Security

Security on a homeserver follows the principle of least privilege: only services that genuinely need to receive traffic should have open ports, and administrative access should never be exposed to the public internet.

On modern Debian Bookworm / Raspberry Pi OS, packet filtering is managed by the kernel’s nftables engine. For straightforward and readable management, we use ufw (Uncomplicated Firewall) on the host:

sudo apt update && sudo apt install -y ufw

Configure firewall rules:

# 1. Set default policies: block all incoming traffic, allow all outgoing traffic
sudo ufw default deny incoming
sudo ufw default allow outgoing

# 2. Allow SSH ONLY from your local home network (e.g. 192.168.178.0/24)
# (Adjust the subnet to match your home router's IP range if different!)
sudo ufw allow from 192.168.178.0/24 to any port 22 proto tcp comment 'SSH local only'

# 3. Allow incoming HTTP and HTTPS traffic from anywhere (for Caddy)
sudo ufw allow 80/tcp comment 'Caddy HTTP ACME'
sudo ufw allow 443/tcp comment 'Caddy HTTPS TLS'

# 4. Allow Nextcloud AIO setup interface strictly from your local network
sudo ufw allow from 192.168.178.0/24 to any port 8080 proto tcp comment 'Nextcloud AIO Mastercontainer'

# 5. Enable the firewall
sudo ufw enable

Check firewall status:

sudo ufw status verbose

[!NOTE] Docker and Firewall Chains: Docker by default manipulates iptables/nftables directly using its own DOCKER-USER chain. Because of this, our application containers (Vaultwarden, Immich, Homebox) only expose ports to 127.0.0.1 (localhost), forcing all inbound public traffic to pass exclusively through Caddy on port 443. Fail2ban (configured in Chapter 5) monitors Caddy logs and dynamically injects IP blocks directly into the DOCKER-USER chain.

Optional: Remote Desktop (xrdp)

If you ever need a graphical desktop for partition tools (like GParted) without plugging in a physical monitor:

sudo apt install -y xrdp
sudo systemctl enable --now xrdp
sudo ufw allow from 192.168.178.0/24 to any port 3389 proto tcp comment 'Remote Desktop local'

You can now connect from Windows using Remote Desktop Connection (mstsc.exe) or Remmina on Linux to kronos.local with user hsa.

3.3 Custom Administrative Scripts

To make everyday maintenance effortless, we place small helper scripts into /usr/local/sbin/. These scripts give you single-command workflows for updates, container control, and hardware telemetry.

1. System Updater (uuc - Update & Upgrade Clean)

Updates OS packages, installs security patches, and cleans up old package archives in one command:

sudo nano /usr/local/sbin/uuc

Paste:

#!/bin/bash
set -e
echo "==> Updating package indices..."
sudo apt update
echo "==> Upgrading installed packages..."
sudo apt -y upgrade
echo "==> Applying distribution upgrades..."
sudo apt -y dist-upgrade
echo "==> Removing orphaned dependencies..."
sudo apt -y autoremove --purge
echo "==> Cleaning package cache..."
sudo apt clean
echo "==> System update complete!"

Make it executable:

sudo chmod +x /usr/local/sbin/uuc

2. Docker Stack Controller (docker-up & docker-down)

Nextcloud AIO manages its subordinate containers (database, Redis, Apache, Collabora) through its mastercontainer. Running a plain docker compose down would leave those child containers running in an orphaned state. These scripts ensure clean, graceful startups and shutdowns:

Create /usr/local/sbin/docker-down:

sudo nano /usr/local/sbin/docker-down

Paste:

#!/bin/bash
cd /etc/hs_docker || exit 1

echo "==> Gracefully stopping Nextcloud AIO child containers..."
docker exec -t nextcloud-aio-mastercontainer su-exec www-data php /var/www/docker-aio/php/src/Cron/StopContainers.php 2>/dev/null || echo "Mastercontainer inactive; continuing..."

echo "==> Tearing down main Docker Compose stack..."
docker compose -f /etc/hs_docker/docker-compose.yml down
echo "==> Stack stopped cleanly."

Create /usr/local/sbin/docker-up:

sudo nano /usr/local/sbin/docker-up

Paste:

#!/bin/bash
cd /etc/hs_docker || exit 1

echo "==> Starting main Docker Compose stack..."
docker compose -f /etc/hs_docker/docker-compose.yml up -d

echo "==> Waiting for mastercontainer initialization..."
sleep 10

echo "==> Starting Nextcloud AIO subordinate containers..."
docker exec -it nextcloud-aio-mastercontainer su-exec www-data php /var/www/docker-aio/php/src/Cron/StartAndUpdateContainers.php 2>/dev/null || true
echo "==> All homeserver services are up and operational!"

Create /usr/local/sbin/udc (Update Docker Containers):

sudo nano /usr/local/sbin/udc

Paste:

#!/bin/bash
set -e
cd /etc/hs_docker || exit 1

echo "==> Stopping running services..."
/usr/local/sbin/docker-down

echo "==> Pulling latest container images..."
docker compose -f /etc/hs_docker/docker-compose.yml pull

echo "==> Re-launching stack with updated images..."
/usr/local/sbin/docker-up

echo "==> Pruning unused dangling images..."
docker image prune -f
echo "==> Container updates finished successfully!"

Make them executable:

sudo chmod +x /usr/local/sbin/docker-down /usr/local/sbin/docker-up /usr/local/sbin/udc

3. Real-Time Telemetry (cpustats)

Create /usr/local/sbin/cpustats to monitor live temperatures, clock speeds, and thermal throttling in real time:

sudo nano /usr/local/sbin/cpustats

Paste:

#!/bin/bash
while true; do
  clear
  echo "=== Kronos CPU Telemetry ==="
  echo "Timestamp:   $(date '+%Y-%m-%d %H:%M:%S')"
  echo "Temperature: $(vcgencmd measure_temp)"
  echo "Core Clock:  $(( $(vcgencmd measure_clock arm | cut -d= -f2) / 1000000 )) MHz"
  echo "Core Volts:  $(vcgencmd measure_volts core)"
  echo "Throttling:  $(vcgencmd get_throttled)"
  sleep 2
done

Make it executable:

4.2 Router Port Forwarding

On your home internet router (e.g. AVM FRITZ!Box, Asus, Netgear, pfSense):

  1. Assign a Static Local IP: In your router’s DHCP settings, check the box: “Always assign this network device the same IPv4 address” (e.g. 192.168.178.50).
  2. Forward Ports:
    • Port 80 TCP (HTTP) $\rightarrow$ Forward to 192.168.178.50:80 (Required by Caddy to answer automated ACME Let’s Encrypt validation challenges).
    • Port 443 TCP (HTTPS) $\rightarrow$ Forward to 192.168.178.50:443 (All production encrypted traffic).

[!IMPORTANT] Never forward Port 22 (SSH) or Port 8080 (AIO Admin) to the public internet. Administrative access should only ever happen from within your home network or via an encrypted WireGuard VPN.

4.3 Understanding IPv4 vs. IPv6

  • IPv4 (Standard & Recommended for Beginners): Standard home internet connections use NAT (Network Address Translation). Your router has one public IPv4 address, and port forwarding sends traffic arriving on ports 80/443 to the local IP of your Raspberry Pi. This is the simplest approach and works out of the box.
  • IPv6 (Optional): In IPv6, there is no NAT—every device receives its own globally routable IPv6 address.
    • If your home router (such as a FRITZ!Box) and your ISP support native IPv6 or DS-Lite, you can enable IPv6 port sharing (Portfreigabe) for the Raspberry Pi’s IPv6 address on ports 80 and 443.
    • While modern Caddy and Docker support IPv6 natively, configuring IPv6 dynamic DNS requires extra care (updating AAAA records). If you have standard IPv4 or Dual-Stack, standard IPv4 port forwarding is all you need to get everything working reliably.

4.4 NAT Hairpinning & DNS Rebind Protection

When you are sitting on your sofa connected to home Wi-Fi and open https://nextcloud.example.com, your laptop asks for the IP of nextcloud.example.com. The public DNS answers with your home router’s external WAN IP.

Your router must support NAT Hairpinning (NAT Loopback) to recognize that this public IP belongs to itself, routing the request immediately back to the Raspberry Pi instead of failing.

Furthermore, many routers (notably FRITZ!Box) contain DNS Rebind Protection to prevent malicious websites from querying local network IPs:

  • In FRITZ!Box: Navigate to Home Network (Heimnetz) $\rightarrow$ Network (Netzwerk) $\rightarrow$ Network Settings (Netzwerkeinstellungen) $\rightarrow$ DNS Rebind Protection. Add your subdomains:
    nextcloud.example.com
bitwarden.example.com
immich.example.com
homebox.example.com

4.5 Dynamic DNS (DynDNS)

Because most home internet connections change their public IP address periodically, DynDNS ensures your domain always points to your current router IP.

Option A: Router-Managed DynDNS (Recommended)

If your router natively supports DynDNS updates, configure your provider’s update URL directly in the router’s settings (e.g. in FRITZ!Box under Internet $\rightarrow$ Permit Access (Freigaben) $\rightarrow$ DynDNS).

5.7 Fail2ban Multi-Jail Intrusion Defense

Fail2ban actively monitors incoming logs from Caddy, Vaultwarden, and Nextcloud. When brute-force patterns or unauthorized probe attempts are detected, it dynamically writes firewall ban rules into the DOCKER-USER chain.

The Dual-Jail Strategy:

  • Short Jails: Ban rapid automated bots immediately (e.g. 3 failed attempts in 3 minutes $\rightarrow$ banned for 5 minutes).
  • Long Jails: Ban persistent, slow password sprayers (e.g. 5 failed attempts across an hour $\rightarrow$ banned for 24 hours).
  • Admin Panel Jails: Immediate zero-tolerance ban for anyone probing /admin endpoints from unauthorized networks.

Helpful Monitoring Commands:

# Check status of all active protection jails
docker exec fail2ban fail2ban-client status

# Check details of a specific jail (e.g. nextcloud-long)
docker exec fail2ban fail2ban-client status nextcloud-long

# List all currently banned IP addresses
docker exec fail2ban fail2ban-client banned

# Manually unban an IP address (if you accidentally locked yourself out)
docker exec -t fail2ban fail2ban-client set <jail_name> unbanip <IP_ADDRESS>

7. Automated Encrypted Backups & Disaster Recovery

A homeserver is only as dependable as its restore strategy. We employ encrypted, deduplicated BorgBackup snapshots stored on an independent secondary drive.

7.1 Mounting the Secondary Backup Hard Drive

  1. Connect your external USB hard drive (e.g. 4TB+) to the second USB 3.0 port.
  2. Obtain its partition UUID:
    sudo blkid -o export /dev/sdb1
  3. Create the mount folder:
    sudo mkdir -p /mnt/backup-hdd
  4. Add the drive to /etc/fstab with nofail and x-systemd.automount so the Raspberry Pi boots cleanly even if the drive is unplugged:
    PARTUUID=<PARTUUID-OF-BACKUP-DRIVE>  /mnt/backup-hdd  btrfs  defaults,nofail,x-systemd.automount  0  0
  5. Mount the drive and grant ownership to hsa:
    sudo mount /mnt/backup-hdd
sudo chown -R hsa:hsa_group /mnt/backup-hdd

7.2 Nextcloud AIO Automated BorgBackup

  1. Open the Nextcloud AIO setup interface (https://kronos.local:8080).
  2. Under BorgBackup, set the backup directory to:
    /mnt/backup-hdd
  3. Save your encryption passphrase: Copy the generated passphrase and store it in your offline records. If you ever lose this passphrase, encrypted backups cannot be recovered.
  4. Add additional persistent directories to the backup set:
    /mnt/sda4/vwdata
/mnt/sda4/immichdata
/mnt/sda4/homeboxdata
  5. Run your initial backup. Future backup runs will execute automatically every night, taking only minutes because Borg only transfers new and modified file blocks.

7.3 Extracting a Single File from a Borg Backup

If you ever accidentally delete or overwrite an important file, you do not need to restore the whole server. You can mount any Borg snapshot as a virtual folder and copy individual files directly.

Step 1: List Available Snapshots

sudo borg list /mnt/backup-hdd

Output shows snapshots with timestamps:

2026-10-18_04:00:01                  Sun, 2026-10-18 04:00:05
2026-10-19_04:00:01                  Mon, 2026-10-19 04:00:04
2026-10-20_04:00:01                  Tue, 2026-10-20 04:00:05

Step 2: Mount the Snapshot

sudo mkdir -p /tmp/borg-mount
sudo LC_ALL=C.UTF-8 borg mount /mnt/backup-hdd::2026-10-20_04:00:01 /tmp/borg-mount

Enter your Borg passphrase when prompted.

Step 3: Copy Your File

The snapshot appears as a read-only directory:

# Locate and copy the file
sudo cp "/tmp/borg-mount/mnt/sda4/ncdata/data/hsa/files/Documents/Contract.pdf" ~/recovered_contract.pdf
sudo chown hsa:hsa ~/recovered_contract.pdf

Step 4: Unmount the Archive

Always unmount the snapshot when finished so the repository is unlocked for nightly backups:

sudo borg umount /tmp/borg-mount
Troubleshooting: PostgreSQL Timezone Dump Error

If the Nextcloud AIO backup fails with FATAL: invalid value for parameter "TimeZone": "CEST":

  1. Ensure the system timezone is set properly:
    sudo timedatectl set-timezone Europe/Berlin
  2. Start the database container and open a shell:
    sudo docker start nextcloud-aio-database
sudo docker exec -it nextcloud-aio-database bash
  3. Locate postgresql.conf, set timezone = 'Europe/Berlin', and save.
  4. Restart the mastercontainer:
    docker compose down && docker compose up -d

8. Daily Operation, FAQ & Routine Maintenance

Your homeserver is now running a hardened, modern cloud suite with automated maintenance:

  • Nightly Container Updates: Watchtower checks and pulls updated images at 04:00 daily.
  • Weekly System Hygiene: Run uuc to update base OS security packages, and udc to refresh container layers.
  • Live Monitoring: Run cpustats for temperature and throttling checks.
  • Security Check: Run docker exec fail2ban fail2ban-client status to review active protection jails.

8.1 Frequently Asked Questions (FAQ)

Q1: How do I update the server and my Docker containers?

  • Base Operating System: Run uuc anytime from your shell. It updates Debian packages, applies kernel security updates, and removes obsolete libraries.
  • Docker Containers: Watchtower updates running containers automatically every night at 04:00. If you want to force an immediate update of all containers, run udc.

Q2: How do I add a new Docker container service (e.g. Pi-hole, Home Assistant, Jellyfin)?

Adding a new service is simple:

  1. Open /etc/hs_docker/docker-compose.yml and add your service block. Connect it to a network bridge and bind its port to 127.0.0.1:<port>.
  2. Add a subdomain in your DNS registrar (e.g. homeassistant.example.com).
  3. Add a routing block to /etc/hs_docker/Caddyfile:
    https://homeassistant.example.com:443 {
    import security_header
    reverse_proxy homeassistant:8123
}
  4. Reload Caddy without downtime:
    docker exec -w /etc/caddy caddy caddy reload

Q3: What should I do if my home IP changes and the domains are unreachable?

  1. Check if your router or ddclient successfully updated your DNS records:
    nslookup nextcloud.example.com 1.1.1.1
  2. Compare the output to your current public IP address:
    curl -4 ifconfig.me
  3. If they differ, trigger a manual update in your router settings or restart ddclient:
    sudo systemctl restart ddclient

Q4: How do I monitor disk usage, health, and temperatures?

  • Temperatures & CPU: Run cpustats to inspect live clock speeds and thermals.
  • Disk Free Space: Run df -h /mnt/sda4 /mnt/backup-hdd to check available space on your data and backup partitions.
  • Btrfs Filesystem Health: Run sudo btrfs filesystem usage /mnt/sda4 to see allocation and deduplication efficiency.

Q5: How do I safely reboot or power off the homeserver?

Never pull the power plug directly, as this could interrupt ongoing database transactions! Always shut down cleanly:

# 1. Gracefully stop containers
sudo docker-down

# 2. Reboot or power down
sudo reboot
# (or 'sudo poweroff' if you plan to disconnect the power)

Q6: Nextcloud says “Service Unavailable - Maintenance mode active”. How do I fix it?

If an unexpected shutdown happens during a Nextcloud app update, Nextcloud may stay in maintenance mode. You can disable it from the command line:

sudo docker exec --user www-data nextcloud-aio-nextcloud php occ maintenance:mode --off
